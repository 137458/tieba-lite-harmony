# PRD：楼中楼预览按时间排序

## Problem Statement

当前论坛帖子卡片的楼中楼预览依赖服务端 `hot_post_list`，其返回的子回复顺序不保证按发布时间排列。用户希望卡片中已展示的回复按回复时间预览；同时，进入回复超过十条的楼中楼时会出现明显卡顿。

## Solution

帖子详情页 PbPage 请求对齐原应用发送 `with_floor=1` 与 `floor_rn=4`，让每条普通回复直接携带 `Post.sub_post_list` 预览。若服务端仍省略预览，则按可视楼层通过 PbFloor 使用 `tid+pid` 精确补取第一页，按回复时间倒序展示至多三条。补请求按 `tid+pid` 共享缓存，避免楼层复用后重复请求；预览固定位于正文/媒体之后、操作栏之前。完整楼中楼页继续通过评论接口分页加载，并保持增量列表路径，避免超过十条回复时的同步集中阻塞。

## User Stories

1. 作为浏览吧内帖子的用户，我希望卡片预览按回复时间排列，以便先看到最新讨论。
2. 作为浏览有多条楼中楼回复的用户，我希望预览只显示最新的有限条数，以便帖子列表保持紧凑。
3. 作为浏览无楼中楼回复的用户，我希望卡片不出现空白预览区域。
4. 作为打开完整楼中楼列表的用户，我希望现有独立分页功能保持不变。
5. 作为维护者，我希望主 PbPage 请求直接携带楼中楼预览，并仅为缺少预览数据的可视楼层请求 PbFloor，以便预览不会因首屏字段缺失而消失。
6. 作为打开回复超过十条楼中楼的用户，我希望页面能够平稳进入并开始滚动，以便不会因回复数量增加出现明显停顿。
7. 作为发送楼中楼回复的用户，我希望成功后只同步必要的数据，以便不会因为整表重建而丢失滚动连续性。

## Implementation Decisions

1. `SubPostInfo.createTime` 是已解码的稳定时间字段；普通回复使用 PbPage 或 PbFloor 返回的首屏子回复，按它倒序取得至多三条。
2. PbPage 请求发送原应用使用的 `with_floor=1` 与 `floor_rn=4`；只有 `replyNum > 0` 且 `subPostList` 为空的可视楼层才按 `tid+pid` 请求 PbFloor，并缓存该楼层结果。
3. 独立楼中楼页保持评论接口及页码分页语义；首次进入仍可替换数据源，加载更多必须继续使用增量追加。
4. 楼中楼头像由同步加载改为异步加载，保留低质量插值和占位图，避免初始可见项集中解码阻塞首帧。
5. 回复发送成功后不直接触发整个数据源刷新；需要以服务端返回的完整楼中楼对象进行局部插入。若当前回帖接口无法提供该对象，则保留刷新行为并将此能力列为后续接口补充，不伪造本地数据。
6. PbPage 的上一页锚点、最新回复锚点与时间倒序分页需另行按 protobuf 字段定义和原 Android 应用的游标策略修复，不把未经证实的协议调整混入本次卡片/楼中楼页面性能切片。

## Testing Decisions

1. 使用创建时间先后不同、热度相反的 `SubPostInfo` 数据验证卡片按时间倒序输出至多三条回复。
2. 验证无子回复帖子不显示预览，独立楼中楼页的分页与加载更多不受影响。
3. 在真机或模拟器中测量打开含十条以上回复的楼中楼时，从路由完成到首个可滚动列表帧的耗时，并与修改前对比。
4. 使用 Hvigor 构建验证 ArkTS 编译通过。

## Out of Scope

1. 不新增客户端可切换的回复排序设置。
2. 不改变独立楼中楼页的分页排序语义。
3. 不对所有论坛卡片一次性请求 PbPage 或 PbFloor 接口；请求只发生在可视卡片生命周期。
4. 不在本切片中调整 PbPage 的上一页/倒序分页协议字段。

## Further Notes

FrsPage 的 `hot_post_list` 仍是服务端选择的热评；本需求承诺的是其已下发子回复的时间顺序，而不是将热评主回复替换为整帖范围的最新评论。卡片预览与楼中楼进入性能作为两个关联的垂直切片实施。
