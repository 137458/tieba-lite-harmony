# HarmonyOS 类似项目移植开发指南

适用对象：将已有 Android、iOS、Web 或开源客户端迁移为 HarmonyOS NEXT 原生应用的项目。本文以“复用产品行为与公开协议、在 HarmonyOS 上独立实现客户端”为前提，不要求也不建议直接复制其他平台的 UI 或业务代码。

## 1. 核心原则

1. 先确认行为，再实现代码。页面流程、接口参数、字段编号、登录状态与异常分支必须以原客户端、协议资料或抓包证据为依据。
2. 先查官方样例和 API 文档，再调用 HarmonyOS API。不要根据 Android、iOS 或 Web 的习惯猜测 ArkUI、Kit 与权限接口。
3. 原生体验优先。功能逻辑可参考源端，视觉结构、导航、菜单、弹窗、输入法适配和动画优先采用 ArkUI 与 HDS 的原生模式。
4. 每个迁移功能都要具备验证路径。最少应包含编译验证与真机/模拟器行为验证；涉及协议时还需有可重放的请求与响应样本。
5. 不把第三方账号凭据、密钥、Cookie 或抓包中的个人信息提交进仓库或写入日志。

## 2. 推荐迁移流程

### 2.1 建立证据库

在开始编码前，整理并固定以下来源：

- 原应用：页面入口、交互状态、加载和失败反馈、登录前后差异。
- 协议资料：公开 API、开源客户端实现、Protobuf 定义、网络抓包或服务端文档。
- HarmonyOS 官方资料：开发者文档、SDK 类型定义和本地官方示例。
- 兼容性矩阵：目标 API Level、目标设备类型、最低系统版本、是否需要平板/折叠屏。

建议为每一个功能建立“行为证据 → HarmonyOS 实现 → 验证记录”的映射。这样接口变更或视觉回归时可以快速追溯，而不是反复猜测。

### 2.2 先打通纵向切片

优先完成一个可演示的端到端功能，而不是先铺满所有页面：

1. 路由入口与参数校验。
2. 请求构造、鉴权和响应解析。
3. ViewModel/状态层。
4. ArkUI 页面与错误/空/加载状态。
5. 编译和真机验证。

例如先完整实现“帖子详情读取 → 富文本展示 → 点赞 → 失败回滚”，再扩展分页、排序、楼中楼和上传能力。这样能尽早验证协议、状态和 UI 三层的契合度。

### 2.3 修复问题的标准流程

1. 复现：记录最短路径、设备系统版本、登录态和网络条件。
2. 对照：查看原应用或协议参考的同一场景，确认预期行为。
3. 查证：从官方文档与官方样例确认 ArkUI/Kit API 的名称、参数、权限和 API Level。
4. 最小修复：只改导致问题的责任层；不要用页面级“补丁”掩盖状态、协议或生命周期问题。
5. 回归：重新验证原始路径、相邻页面、深浅色与输入法/旋转等系统状态。

## 3. 工程基线

### 3.1 版本与构建

- 新项目使用 Stage 模型和 ArkTS；不要为新代码引入 FA 模型。
- 生产项目优先采用当前稳定 SDK。若使用预览 API，必须将 API 版本、设备范围和降级策略写入文档。
- SDK、DevEco Studio、Hvigor、Node.js 与 OHPM 版本保持由 DevEco 生成的组合，避免手工混搭。
- SDK 版本只在构建配置的一处声明，避免 `app` 与 `product` 重复设置造成同步失败。
- 每次改动后至少执行一次 `assembleHap`；发布前执行完整签名、混淆和真机安装验证。

### 3.2 推荐目录职责

```text
entry/src/main/ets/
  entryability/   应用入口、窗口和启动任务
  pages/          路由页面与页面级状态编排
  components/     可复用 ArkUI 组件
  model/          领域模型、可观察状态模型
  viewmodel/      分页、加载、错误与业务状态
  api/            HTTP/Protobuf/WebSocket 等协议适配
  proto/          协议编码、解码与字段定义
  utils/          无 UI 依赖的通用工具
entry/src/main/resources/
  base/           默认字符串、颜色、媒体和 profile
  dark/           深色模式同名资源覆盖
  zh_CN/en_US/    多语言字符串覆盖
docs/
  迁移决策、协议证据、真机验证记录、已知限制
references/
  原客户端、协议定义、HarmonyOS 官方样例，仅作参考而非运行依赖
```

页面只负责展示和用户操作编排；请求、协议解析、分页推进、凭据读取和复杂状态不要直接堆在页面内。

## 4. 协议与数据迁移

### 4.1 先分清协议类型和鉴权方式

同一个服务常同时存在 Web、JSON、Protobuf、WebSocket 等端点，它们可能使用不同的鉴权载体。迁移时必须为每种端点明确记录：

- URL、HTTP 方法、编码格式、请求头和超时策略。
- Cookie、Authorization、请求体公共字段等认证位置。
- 成功码的数字/字符串兼容规则。
- 分页字段、默认值语义、排序字段及错误码。

不要假设“登录成功就所有接口可用”。例如 Web 请求可能依赖 Cookie，而 Protobuf 请求可能要求在公共请求字段中携带会话凭据。

### 4.2 Protobuf 或二进制协议

- 优先使用服务端公开的 `.proto` 或可信字段定义；字段编号、wire type 和嵌套消息不能凭字段名推测。
- 若手写编解码，单独封装 reader/writer，并用真实响应样本建立回归测试。
- proto3 默认值与“服务端未返回字段”不能混为一谈；分页推进应在客户端维护明确状态，刷新失败需要回滚。
- 解析异常应转化为可理解的业务错误；不要让底层越界、空值或解码异常直接崩溃页面。

### 4.3 参数与时序守卫

路由参数必须在异步操作前读取、校验并写入 ViewModel。所有数据加载入口都要拒绝无效关键参数，例如 `id <= 0` 时不发请求。这样可避免页面生命周期中 `await` 造成默认值请求、错误码和错误内容闪烁。

## 5. ArkTS 与状态管理

### 5.1 按 ArkTS 约束设计模型

ArkTS 不是完整 TypeScript。迁移时应主动规避动态语言写法：

- 不使用 `any`、`unknown`、动态字段访问、对象解构、`for...in`、`Function.bind/call/apply`。
- 为请求、响应、页面参数、事件回调定义显式类或接口。
- 类字段在类体中声明并初始化；数组元素类型保持一致。
- 回调用箭头函数，避免 `this` 上下文丢失。
- 导入必须在文件开头，避免在运行时动态拼装模块能力。

### 5.2 优先使用 V2 状态管理

适合新页面的默认组合：

- `@ComponentV2 + @Local`：组件内部状态。
- `@Param + @Event`：父子组件数据传入与事件回传。
- `@ObservedV2 + @Trace`：领域对象和深层数据变化。
- `@Monitor`：响应状态变化后的收敛逻辑。
- `AppStorageV2`：跨页面共享的内存状态。
- `PersistenceV2` 或 preferences：需要跨启动保存的设置。

`AppStorageV2` 只负责运行期共享，不自动持久化。可持久化设置需要在写入时同步保存，在启动任务完成后恢复，并考虑旧 key 的一次性迁移。

### 5.3 TaskPool 与 Worker 的边界

- TaskPool 用于可分割、CPU 密集且不依赖 UI 的任务，例如复杂二进制解析或图片处理。
- `@Concurrent` 函数不能捕获外层状态，不能依赖 UIContext、AppStorage 或页面对象。
- 不要向 TaskPool 传递 enum；跨线程传递时可能出现值丢失。改传数字或字符串常量。
- AppStorageV2 不可作为子线程共享存储；子线程只返回纯数据，由主线程写回状态。
- 长生命周期、持续消息或独立状态场景再使用 Worker，并在页面销毁时终止或解绑。

## 6. UI 原生化与视觉迁移

### 6.1 迁移行为，不照搬平台外观

将源端视觉需求翻译为 HarmonyOS 的对应构件：

- 页面导航：`Navigation`、`NavPathStack`、`HdsNavigation`、`HdsNavDestination`。
- 列表和分页：`List + LazyForEach`、`Grid`、`WaterFlow`。
- 菜单：`bindMenu` 或 HDS 标题栏菜单。
- 弹窗/半模态：`openCustomDialog`、`bindSheet`、`openBindSheet`。
- 动画：状态驱动的 `UIContext.animateTo`、`TransitionEffect`、`geometryTransition`。
- 视觉材质：`backgroundBlurStyle`、`linearGradientBlur`、HDS `systemMaterialEffect`。

不要用大量绝对定位或 Android/iOS 风格的手写遮罩模拟系统控件。优先从原生组件的配置能力寻找等价效果。

### 6.2 HDS 与沉浸光感

- 使用 HDS 组件时优先让外层 HDS 承担沉浸光感材质；内部不要重复叠加模糊、纯色背景和圆角，避免出现白色内层或材质断层。
- HDS 的 API 可用性与目标 API Level 有关。需要并列 miniBar、复杂浮动布局前，先确认对应 SDK 是否支持。
- 单 Tab 的 HdsTabs 若出现“圆球”而不是完整胶囊，检查是否显式设置了适合设备尺寸的 `barWidth`。
- HDS 菜单项要提供文本标签；`maxCount` 需按“包含更多按钮本身”的规则配置。

### 6.3 深色模式与资源

- 所有用户可见字符串、色值、尺寸和图标优先使用 `$r()` 资源引用。
- 新增字符串要同步所有已支持语言；格式化字符串使用 `%s`，不要使用 HiLog 专用的 `%{public}s`。
- 深色模式使用 `resources/dark` 的同名资源覆盖，而非在组件中到处判断颜色模式。
- 组件背景要与父容器色阶协调。深色模式下避免在卡片中使用纯黑页面背景造成“黑色遮罩”；需要层次时使用略浅的输入背景色或透明背景。

### 6.4 输入法与 Sheet

输入型 Sheet 必须同时验证系统关闭入口和键盘避让：

```ts
.bindSheet($$this.visible, this.editorBuilder(), {
  height: SheetSize.LARGE,
  showClose: false,
  keyboardAvoidMode: SheetKeyboardAvoidMode.RESIZE_ONLY,
})
```

- 自定义顶栏时显式 `showClose: false`，否则系统 X 与自定义返回/发送按钮可能叠加。
- 编辑区域使用 `layoutWeight(1)`，底部工具栏使用固定高度；`RESIZE_ONLY` 会压缩中间区域，使工具栏保持在键盘上方。
- 键盘相关问题优先参考官方 BindSheet 样例，不要先监听键盘高度进行手动位移。

## 7. 安全、登录与隐私

### 7.1 凭据存储

- Token、Cookie、会话凭据和私钥使用 Asset Store Kit 或系统安全存储，禁止写入普通 preferences、源码、日志或异常提示。
- 旧版本迁移时，每一项凭据独立迁移；安全写入成功后立即清除旧明文 key。
- 登出必须是事务性流程：删除安全存储、清理 Web Cookie、确认成功后再清空内存登录态和路由。任一步失败都不能伪造“已退出”。

### 7.2 Web 登录与外部链接

- WebView 只允许 HTTPS 及明确的可信主机白名单。
- 登录成功判定需覆盖服务实际落地路径，不能只匹配过窄的静态 URL。
- 外部跳转、深链参数和 Web 回调都属于不可信输入，必须校验 host、path、类型和范围。

### 7.3 权限

每个 user_grant 权限都需要同时完成：

1. 在 `module.json5` 声明权限、`reason` 和 `usedScene`。
2. 在使用场景前检查并发起运行时授权。
3. 对拒绝、永久拒绝和系统不支持提供明确降级或引导。

不要仅因“以后可能用到”就声明高风险权限。

## 8. 性能与稳定性

- 长列表使用 `LazyForEach` 与稳定、唯一的 key；列表项优先使用 `@ReusableV2`。
- `build()` 保持纯渲染，不在其中发请求、创建重资源或改状态。
- 首屏优先：窗口加载成功后再触发非关键网络预取；耗时解析移出主线程。
- 图像按场景缩放与延迟加载，离屏释放播放器、监听器和大对象。
- 监听器使用具名回调并在 `aboutToDisappear()` 解绑，避免页面泄漏和重复订阅。
- 动画优先改变 `opacity`、`translate`、`scale` 等变换属性，避免连续修改宽高、内外边距造成反复布局。
- 对崩溃、解析失败、网络失败建立分层错误显示；不要仅依赖控制台日志。

## 9. 验证清单

### 9.1 每次代码变更

- [ ] 运行 ArkTS 编译与 HAP 构建。
- [ ] 检查新增 API 是否符合目标 API Level、导入、权限和设备支持要求。
- [ ] 检查字符串、颜色和图标是否使用资源，是否补齐深色和多语言。
- [ ] 检查错误路径、空数据、重复点击和网络中断。
- [ ] 检查新增监听器、定时器、任务和 WebView 是否有退出清理。

### 9.2 交互页面

- [ ] 冷启动、热启动、前后台切换、旋转或窗口尺寸变化。
- [ ] 登录前后、权限授予/拒绝、弱网/断网、接口业务失败。
- [ ] 深色模式、字体缩放、手机与平板/折叠屏。
- [ ] 输入框、软键盘、Sheet、弹窗、系统返回与手势返回。
- [ ] 长列表分页、刷新失败回滚、重复触发和滚动性能。

### 9.3 发布前

- [ ] 真机安装已验证核心链路，不只依赖 Previewer。
- [ ] release 签名、包名、应用名、vendor、权限说明和隐私说明正确。
- [ ] ArkGuard 规则保留 JSON、数据库列、反射/动态访问、Worker 路径和路由表必要名称。
- [ ] 没有调试凭据、个人 Cookie、测试账号、内部地址和敏感日志。

## 10. 参考与交付物

- `迁移范围.md`：已迁移能力、未迁移能力、源端差异和设备范围。
- `协议证据.md`：每个端点的来源、字段、认证、错误码和样本。
- `架构决策记录.md`：状态管理、导航、协议解析、安全存储、线程模型等关键选择。
- `真机验证记录.md`：设备型号、系统版本、构建号、测试路径、截图/日志与已知问题。
- `兼容性矩阵.md`：SDK/API Level、设备形态、权限、系统能力和降级行为。

## 11. 结论

高质量移植不是把另一平台的页面逐张重画，而是以证据复现产品行为，以 HarmonyOS 原生架构承载状态和协议，并在安全、性能、输入法、深色模式与多设备上完成闭环验证。先确认、再实现、后验证，是这类项目持续可维护的最低成本路径。
